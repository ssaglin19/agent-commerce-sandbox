## Clairic extraction experiment (Oct 19, 2026)
Scoped test of Cloudflare's Clairic (preview) as a fact extractor for the judge: it pulls typed receipt fields and verbatim chat claims (opt-outs, heavy-use claims, disputes, promises). It never assigns weights or verdicts; the judge still weighs the facts. Owner approved this scoped test Oct 19.
- Code: src/haggle/extract.py (Cloudflare provider via CLOUDFLARE_ACCOUNT_ID + CLOUDFLARE_API_TOKEN from env only, plus a deterministic mock with the same interface; hard call budget, live failures raise instead of silently mocking; output can never contain weight/share/verdict keys).
- Harness: scripts/clairic_extraction_check.py runs six synthetic cases with known ground truth, including a claim that contradicts the receipt and an injection-style chat line. One call per case (6 total live), answers persisted to tests/fixtures/clairic_extract_<source>.json so regression never re-calls. Six bounded cases are a smoke check, not an accuracy measurement.
- Mock status: 6/6 cases pass offline; 44 unit tests pass (tests/test_extract.py added).
- Live status (Oct 19): RUN ONCE, 6 calls on the free plan via a scoped 1-day token limited to the personal account with Workers AI:Read only; the token was revoked right after the run. Results persisted to tests/fixtures/clairic_extract_clairic.json. 1/6 cases fully passed. Receipt facts (vendor, total, date) extracted correctly in all six cases: the injection-style chat line did not change the total (stayed $168.00), and the missing-fields case returned a null date. The chat-claim list fields (opt_outs, payment_disputes, payment_promises) over-extracted: spurious or partial spans such as speaker names and fragments, and lines counted that were not such claims, so 5 cases failed on those fields only. Verdict: receipt-fact extraction works as tested; chat claim lists do not, without prompt or schema rework. Not wired to the judge; no judge, split, or payment code changed. Text only; vision is not claimed. Any use in the judge path waits for an owner decision.

## Clairic dissection revision (Oct 19, 2026)
Owner steering after the live run: "I think dissecting it using clairic would be a better approach." The revision asks Clairic about one message at a time instead of whole-chat lists.
- Code: src/haggle/extract.py dissect_case. One call per case asks receipt scalars plus one scalar text field per message per claim category (opt_out, heavy_use, promise, paid_claim, dispute; categories are not mutually exclusive). Code attaches the full source line to each detected claim; the model's value is only a presence signal and must pass a verbatim gate (verbatim substring of that message, 4+ chars, not the bare speaker name). Fragments and hallucinated quotes are dropped; a miscategorized verbatim substring can still pass, so the gate reduces false positives without proving categorization. Field types verified against the published input schema (text, number, date, time, datetime, duration, list, estimate, forecast; no enum/boolean type exists, so categories go through text-with-null).
- Harness: scripts/clairic_dissection_check.py reruns the same six synthetic cases with per-message ground truth and persists results including the model's raw answers to tests/fixtures/clairic_dissect_<source>.json. Mock 6/6; 48 unit tests pass (4 new dissect tests including the fragment gate). Offline only: receipt scalars were 18/18 in the Oct 19 live run, but that says nothing about categorical claim detection, which this shape still has to prove live.
- Live validation (Oct 19): RUN ONCE, 6 calls via a second scoped 1-day Workers AI:Read token (revoked right after). Results with raw answers persisted to tests/fixtures/clairic_dissect_clairic.json. 1/6 cases fully passed (missing-fields). What improved: span quality and recall. Every detected claim quote was a meaningful verbatim phrase (no speaker-name or single-word fragments passed the gate), and every true claim in the six cases was detected - no false negatives. What still fails: precision across categories. Refusals got tagged as both opt_out and dispute ("I'm out, not paying for this"), disagreement as opt_out ("We agreed $120, not $168"), and promise over-fired ("Just a sip on weekends for me", "I already paid for everyone"). Confidence does not separate right from wrong: several wrong categories scored higher than the correct one on the same message (opt_out 0.904 wrong vs dispute 0.876 right). Receipt scalars stayed correct everywhere checked, including the injection case (total stayed $168.00). Verdict: dissection fixed localization and recall but not categorization; Clairic with this schema is still not fit to feed claim types to the judge. Regression on six synthetic cases only, not an accuracy measurement. Judge unchanged; not wired to anything.

## Clairic statement-selection stage (Oct 19, 2026)
Third stage, owner said keep working. No category labels: per message Clairic quotes the speaker's explicit statement about paying, usage, price, or the agreement, or null. Code attaches the full source line; labeling and weighing stay with the judge.
- Code: src/haggle/extract.py select_case (same single-call shape and verbatim gate as dissection; output carries statements, not claims-with-categories). Harness: scripts/clairic_statement_check.py, same six cases, per-message ground truth as a key phrase the quote must contain (null where a message should yield no statement, e.g. bare assent "Looks right to me"); defined before the live run, not retuned. Persists to tests/fixtures/clairic_select_<source>.json.
- Mock 6/6; 52 unit tests pass (4 new select tests including fragment/hallucination gate and bare-assent skip).
- Live validation (Oct 19): RUN ONCE, 6 calls via a third scoped 1-day Workers AI:Read token (revoked right after). Results with raw answers persisted to tests/fixtures/clairic_select_clairic.json. 3/6 cases passed (normal-split, missing-fields, injection-style-line). Precision was clean: every returned quote was a correct verbatim phrase covering the expected key phrase, bare assent correctly returned null, and the injection line yielded only "the total was $0" with the receipt total unchanged at $168.00. The failures were omissions, not fabrications: refusals ("I'm out, not paying for this", "Count me out too") and disagreement ("I never agreed to this charge", "That was the price last week") came back as genuine nulls (p_null 0.87-0.95), not gate drops. The instruction wording ("what they will pay") reads too narrowly to cover refusals and disagreement. Three-stage summary on these six synthetic cases: whole-chat lists had fragment spans and wrong membership (1/6); per-message categories had perfect recall but category bleeding (1/6); per-message statement selection had clean precision but a refusal/disagreement recall gap (3/6). A fourth iteration (instructions covering "will NOT pay / disagree") is the obvious next test but needs a fresh owner go. Regression on six synthetic cases only, not an accuracy measurement. Judge unchanged; not wired to anything. Note: for chats this short, code can hand the judge full messages directly; extraction earns its keep as compression on long chats.
